Yes — the sidebar is the mechanism

  
It already exists, and it is exactly what ADR-018 asks for.

  

    packages/tui/src/feature-plugins/sidebar/ registers each panel independently through
    api.slots.register({ order, slots: { sidebar_content } }). That is a slot registry:
    ordered, themed, and additive. ADR-018 requires the board be built as “a new route plus feature-plugin
    slots”, and this is that mechanism, already proven in the fork.
  

  

    An earlier draft of these mockups collapsed evidence, spec and run into ▸ rows in
    the main pane. That was a hand-rolled and worse version of a sidebar that already ships. The sidebar now
    carries the state that is true regardless of which pane you are in, and the main pane is the
    drill-down.

Where each feature lives, and why

  
Placement is the design. Fourteen surfaces sorted into three kinds, not fourteen tabs.

  

    

      
KindSurfacesRule

      
        

          Sidebar
          Subject, Verdict, Gates, Approval, Attempts, Budget, Children
          True regardless of which pane you are in. Docked and in-flow — it collapses, it never floats over content.
        

        

          Route
          Board, Evidence, Spec, Run, Diff, Journal, Stopped, Orchestrator, Parallel, Workflow, Processes
          A place you go to read one thing deeply. Each opens fullscreen; each keeps the sidebar.
        

        

          Dialog
          Rules, Policy, command palette, help
          Reference, consulted and dismissed. Never a destination — you do not live in the gate catalog.
        

      
    

  

  

    The split that matters most is Rules against Policy. Rules are the handbook agents read, and reading
    guides block nothing. Policy is gates.yaml, and every entry in it can stop the
    work. Merging those two screens would put a suggestion and a constraint side by side looking identical,
    which is the confusion this whole project exists to remove.
  


  
What the field already told us

  
Searched across gemini-cli, crush, kilocode, aider and opencode. Full citations in specs/tui-redesign/ux-research.md.

  

    

      
Filed by usersWhat we did

      
        
opencode #41203 — sidebar became a floating overlay, “covers the chat area instead of shrinking it… feels very janky”Sidebar docks and reflows. No overlay, no hover-peek. Try Narrow.

        
opencode #41249 — a user shipped a live subagents sidebar as a plugin and asked for it built in: per-row status, live activity, child sessionsAdopted as the Children panel. Ranex adds each child's approved scope and whether its result was accepted.

        
kilocode #7024 — “indicator that a general agent task is already finished. Maybe a green border”Adopted, changed: state is spelled. A green border alone dies in NO_COLOR and fails colour-blind users.

        
gemini-cli — flicker on render, on resize, on spinner ticks under tmuxWhy lazygit is cited in ADR-018: recompute every frame, diff before writing.

        
crush — “avoid continuous scroll on text generation”The board is a table and never autoscrolls. Streaming is confined to Processes, which pins when you scroll up.

        
crush — terminal shortcuts collide with app shortcutsKeymap-as-data (BOARD-10), so remapping is configuration rather than a fork.

        
gemini-cli — “no context window % display”; opencode — account usage in the sidebarThe Budget panel — and it is where the three-miss stop becomes visible before it fires.

      
    

  

  

    One finding is worth stating plainly: every harness surveyed renders what the agent did. None
    renders whether the result is acceptable and why not — no gate, no evidence, no cause, no approval
    identity, no chain. Their prior art is worth copying for how a terminal should behave, and has nothing to
    say about the thing Ranex is for.
  


  
What the controls prove

  

    Narrow drops the sidebar, which is BOARD-04's declared collapse order in action: the verdict is the
    last thing surrendered, and it moves into the main pane rather than disappearing.
    16 colours uses real xterm values, not softened ones.
    No colour is NO_COLOR, a pipe, or a CI log.
    No Unicode adds glyph fallback.
  


  

    No state is ever carried by a glyph alone. Every verdict is spelled — PASS,
    FAIL, absent, refused — and the
    glyph beside it is redundant. That is why the degraded modes lose nothing: there was never information in
    the tick. It is also what makes the board readable to someone who cannot distinguish red from green.
  


  

    Fourteen surfaces mapped to BOARD-04 … BOARD-22. Gate output, digests and refusal reasons are real, from
    HEAD of the ranex repository; the UX citations are real issues, listed in
